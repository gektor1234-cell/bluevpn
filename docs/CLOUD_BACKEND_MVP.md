# BlueVPN Cloud Backend MVP

Текущая рабочая серверная модель уже поддерживает облачный сценарий Windows MVP:

- пользователь регистрируется на backend;
- backend хранит аккаунт и подписку;
- backend привязывает отдельные устройства через `deviceUid`;
- backend выдаёт отдельный WireGuard-конфиг на каждое устройство;
- backend возвращает отдельный `assignedIp` для каждого устройства;
- клиент хранит локально только сессию, `device_id.txt` и активный WireGuard-конфиг.

## Что уже подтверждено

- API backend живёт на `http://37.220.85.211:8000`
- OpenAPI доступен по `/openapi.json`
- рабочие endpoint:
  - `/api/v1/auth/register`
  - `/api/v1/auth/login`
  - `/api/v1/me`
  - `/api/v1/subscription/me`
  - `/api/v1/client/bootstrap`
  - `/api/v1/client/config`
- один пользователь может получить отдельные конфиги для разных `deviceUid`
- сервер выдаёт разные адреса для разных устройств, например:
  - `10.10.0.16/32`
  - `10.10.0.17/32`

## Что это означает для продукта

Уже сейчас можно построить сценарий:

1. Пользователь скачивает приложение на новый ноутбук.
2. Регистрируется или входит.
3. Клиент создаёт или поднимает `deviceUid`.
4. Backend регистрирует устройство через `bootstrap`.
5. Backend выдаёт персональный WireGuard-конфиг через `client/config`.
6. Клиент пишет конфиг в `C:\ProgramData\BlueVPN\BlueVPNDev1.conf`.
7. Пользователь нажимает `Подключить VPN`.

## Что ещё нужно для коммерческой версии

- серверный список устройств пользователя:
  - показать `deviceUid`, имя устройства, платформу, дату последней активности;
- серверное отключение устройства;
- смена плана и лимитов на backend;
- admin endpoints для управления подписками;
- серверная ротация и отзыв конфигов;
- серверная аудит-таблица:
  - регистрация,
  - bootstrap,
  - выдача конфигов,
  - блокировки устройств,
  - смена тарифа.

## Принцип хранения

- пароли нельзя хранить в открытом виде;
- на backend должны храниться только password hash и служебные данные аккаунта;
- WireGuard-конфиги и ключи должны выдаваться сервером по устройству, а не жить как основной источник истины на клиенте.

## Клиентский принцип

- после успешного `register/login` клиент должен сразу пытаться прогреть:
  - `bootstrap`
  - `client/config`
- если прогрев не удался, вход всё равно можно завершить, но главный экран должен уметь дотянуть конфиг позже.
