# Green VPN: guest-first, отдельный вход и email перед оплатой

Статус: целевой контракт кандидата, без production-развёртывания.

## Пользовательский путь

1. На чистой установке клиент получает серверную гостевую сессию по локальному
   идентификатору устройства.
2. Пользователь сразу видит бесплатный режим Green VPN. Формы регистрации,
   телефона и SMS до оплаты нет.
3. На главном экране, в тарифе и в настройках есть отдельное действие
   `Уже есть подписка? Войти по email`. Оно не создаёт заказ и не открывает
   платёжную страницу.
4. После email-кода отдельный access-маршрут переносит текущее устройство из
   гостевого профиля в существующий аккаунт и проверяет подписку.
5. Если активной подписки нет, клиент явно сообщает об этом и остаётся в
   аккаунте. Оплата не запускается автоматически.
6. При нажатии `Оплатить` клиент отдельно запрашивает email и отправляет
   одноразовый код.
7. Backend не создаёт платёжный заказ, пока email не подтверждён.
8. Если email новый, он заменяет внутренний адрес текущего гостевого профиля.
9. Если email уже существует, пользователь после проверки кода переходит в
   существующий аккаунт. Активная подписка восстанавливается без нового заказа.
10. Только после проверки email клиент создаёт заказ и открывает hosted payment
   page. Право доступа выдаётся только после подтверждения платёжного
   провайдера/webhook, не по возврату браузера.

## Назначение email

- подтверждение оплаты;
- уведомления о продлении и статусе подписки;
- восстановление доступа на другом устройстве;
- запасной вход одноразовым кодом;
- legacy-вход по паролю для уже существующих аккаунтов.

## Инварианты безопасности

- В публичном API нет `/api/v1/auth/phone/*`.
- Гостевая сессия не содержит публичного email.
- Внутренний гостевой адрес детерминированно выводится через HMAC и не
  раскрывает идентификатор устройства.
- Один код имеет назначение (`purpose`), срок действия, лимит попыток и
  одноразовое потребление.
- Код привязки гостя нельзя использовать как обычный код входа.
- Access-вход и checkout используют разные публичные маршруты; access-вход не
  вызывает создание платёжного заказа.
- Гостевой или неподтверждённый пользователь получает
  `email_verification_required` при попытке создать заказ.
- Подтверждение существующего email переключает на существующий аккаунт; гостю
  не копируются платные права.
- Dev-коды запрещены в публичной среде.
- Секреты SMTP и платежей хранятся только в server-side env.

## Совместимость и удаление SMS

Телефонный UI, публичные маршруты, bootstrap-объявление и релизные требования
удалены. Старые SMS-адаптеры, таблицы и колонки базы пока остаются инертными,
чтобы не выполнять рискованную миграцию с удалением данных в том же релизе.
Их можно удалить отдельной миграцией после подтверждения, что ни один старый
клиент не обращается к телефонным endpoints.

## Обязательный release smoke

- Windows: чистая установка -> бесплатное подключение без регистрации.
- Android: чистая установка -> бесплатное подключение без регистрации.
- Оба клиента: `Оплатить` -> реальное письмо -> неверный код отклонён -> верный
  код принят.
- Оба клиента: отдельный `Войти по email` -> реальное письмо -> существующая
  подписка восстановлена без нового заказа и без открытия YooKassa.
- Просроченная гостевая сессия обновляется автоматически и не отправляет
  бесплатного пользователя на обязательный экран входа.
- Новый email продолжает к hosted payment page.
- Существующий email с активной подпиской восстанавливает доступ без нового
  заказа.
- Гостевой прямой запрос заказа отклонён backend.
- После перезапуска клиента гостевая или подтверждённая сессия сохраняется.
- Rollback-артефакт и точные SHA256 подготовлены до продвижения кандидата.
- Production допускается только после физического smoke владельцем и отдельной
  команды на развёртывание.
