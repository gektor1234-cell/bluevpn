# Финальная расширенная дорожная карта Green VPN

Это большой мастер-план Green VPN: Windows-продукт, коммерция, админка, поддержка, обновления, мониторинг доступности сервисов и постепенный путь к “титановому” VPN-layer.

## Важная Поправка

Абсолютно “невозможно заблокировать” не бывает. Если у пользователя полностью выключен интернет, заблокированы все внешние маршруты или физически нет сети, VPN не поможет. Но можно сделать систему, которая переживает блокировки IP, портов, UDP, WireGuard-сигнатур, DNS, API-домена, отдельных стран, отдельных провайдеров и падение серверов.

Наша цель: не “один VPN-протокол на одном сервере”, а многоуровневая система fallback.

## Главная Цель

Сделать Green VPN нормальным коммерческим VPN-продуктом. Пользователь скачивает установщик, устанавливает приложение, регистрируется или входит, выбирает тариф, нажимает подключить, и VPN работает без ручных танцев с админ-правами, конфигами, папками и техническими ошибками.

## 1. Windows Service

Сейчас UI исторически требовал админ-права, потому что WireGuard на Windows требует права для управления сервисом, адаптером и маршрутами. Для настоящего продукта это нужно держать через системный компонент.

Что нужно сделать:

- Установщик один раз просит админ-права.
- Установщик ставит Green VPN Service.
- Сервис работает от LocalSystem или эквивалентно безопасного privileged helper.
- Обычный клиент запускается без UAC.
- UI отправляет сервису команды: подключить, отключить, получить статус, собрать отчёт.
- Сервис управляет `WireGuardTunnel$BlueVPNDev1`, конфигами, handshake, traffic.
- UI больше не должен каждый раз запускаться от имени администратора.
- Service/helper не должен ломать Amnezia, WARP и чужие VPN.

## 2. Tray, Фон И Автозапуск

Приложение должно вести себя как нормальный VPN-клиент.

Что нужно сделать:

- Автоматический запуск вместе с Windows.
- При закрытии окна приложение не закрывается, а уходит в tray.
- В панели задач окно пропадает.
- Иконка остаётся в скрытых значках Windows.
- Через tray можно открыть окно, подключить VPN, отключить VPN, выйти.
- Крестик окна = скрыть приложение.
- Выход через меню tray = реально закрыть UI.
- VPN-сервис продолжает работать независимо от открытого окна.
- Автозапуск не должен автоматически включать VPN поверх Amnezia/WARP/чужого WireGuard без понятной политики.

## 3. Вход И Регистрация

Это один из самых важных блоков, потому что пользователь не должен спотыкаться на первом экране.

Что нужно сделать:

- Полностью перелопатить вход и регистрацию.
- Первичным вариантом сделать телефон/SMS-код, вторичным - email-код.
- Email должен работать не как “подтверждение почты после регистрации”, а как вход по коду.
- После успешной регистрации сразу переводить пользователя в приложение.
- После успешного входа сразу переводить пользователя в приложение.
- Разделить состояния входа и регистрации.
- Показывать понятные ошибки: email уже зарегистрирован, неверный пароль, сервер недоступен, нет сети, превышен лимит устройств.
- Не показывать пользователю SocketException, PathAccessException, backend, bootstrap и другие технические слова.
- Сделать восстановление доступа.
- Сделать нормальное сохранение сессии.
- Сделать понятный выход из аккаунта.
- Сделать аккуратную обработку случая, когда аккаунт создан, но конфиг ещё не выдан.

## 4. Email, SMS И Социальный Вход

Регистрация должна быть удобной для обычных людей, особенно в России.

Порядок:

- Сначала email-код.
- Потом регистрация/вход по телефону через SMS.
- Потом привязка телефона к существующему аккаунту.
- Потом социальные входы.

Возможные варианты входа:

- Email + код.
- Телефон + SMS.
- VK ID.
- Google.
- Возможно Telegram login позже.

Важно: email и телефон делаем последовательно, но backend сразу проектируем так, чтобы у одного аккаунта могло быть несколько способов входа.

## 6. Диагностика Для Поддержки

Обычному пользователю не нужна техническая диагностика в текущем виде.

Что нужно сделать:

- Удалить или сильно упростить экран диагностики.
- Оставить кнопку `Отправить отчет`.
- Не делать основной сценарий через `Скопировать отчет`, если можно отправлять на backend.

- Отчёт должен быть кодированным или зашифрованным.
- Техподдержка должна уметь расшифровать отчёт и понять, что произошло.

Отчёт должен помогать понять:

- Работает ли service/helper.
- Есть ли handshake.
- Есть ли traffic.
- Есть ли ошибка WireGuard.
- Есть ли ошибка авторизации.
- Есть ли ошибка оплаты.
- Есть ли проблема с устройством или лимитом.
- Есть ли competing VPN.
- Есть ли доступ к ключевым сервисам через VPN.

## 7. Тарифы

- Сервер является источником правды по тарифу.
- Кнопка должна быть понятной: Оплатить тариф, Продлить тариф, Изменить тариф.
- Не показывать лишнюю техническую разбивку цены обычному пользователю.

## 9. Бесплатный Режим И Реклама

Это делаем позже, не сейчас.

## 12. Система Обновлений

Обновления обязательно нужны, потому что VPN-продукт будет постоянно меняться: новые сервера, фиксы блокировок, исправления auth, платежи, новые протоколы, безопасность.

Дешёвый первый этап:

- Клиент при запуске проверяет текущую версию.
- Backend отдаёт latestVersion, downloadUrl, sha256, required, changelog.
- Если обновление необязательное, пользователь видит кнопку Обновить.
- Если обновление критическое, приложение просит обновиться перед подключением.
- Установщик скачивается с нашего сервера.
- После скачивания проверяется SHA256.
- Потом запускается обновление.
- VPN-сервис и UI должны корректно обновляться без ручного удаления.

Средний этап:

- Подписанный update manifest.
- Code signing установщика.
- Автоматическое скачивание в фоне.
- Staged rollout: сначала 5%, потом 25%, потом 100%.
- Rollback, если новая версия ломает подключения.
- Разделение обновлений клиента и server catalog.

Сильный этап:

- Нормальный updater вместо ручного скачивания.
- MSIX/App Installer или свой signed updater.
- Возможность silent update для service-компонента.
- Отдельное обновление протокольных модулей.
- Отдельное обновление server catalog без полной переустановки.
- Отдельное обновление правил Social Only.
- Отдельное обновление fallback-логики.

Важно:

- Не все изменения должны требовать обновления приложения.
- Список серверов должен обновляться через backend.
- Правила маршрутизации должны обновляться через backend.
- Аварийные endpoint должны обновляться через подписанный catalog.
- Приложение должно уметь получить “экстренный список серверов”, если главный API недоступен.

## 13. Неубиваемый VPN Layer

Это новый большой слой. Его задача: если один способ подключения заблокирован, приложение автоматически пробует другой.

Базовый принцип:

- Не один сервер.
- Не один протокол.
- Не один порт.
- Не один DNS.
- Не один домен API.
- Не один провайдер VPS.
- Не одна страна.
- Не один способ доставки конфигов.

Что нужно сделать:

- Оставить WireGuard как быстрый основной протокол.
- Добавить fallback-протоколы для случаев, когда WireGuard/UDP режется.
- Сделать автоматический выбор лучшего транспорта.
- Сделать health-check серверов.
- Сделать автообновляемый список серверов.
- Сделать подписанный server catalog, чтобы клиент доверял только нашим endpoint.
- Сделать несколько API-endpoint для bootstrap.
- Сделать fallback, если главный API-домен недоступен.
- Сделать диагностику “почему не подключилось”: DNS, TCP, UDP, TLS, handshake, route.
- Сделать kill switch, чтобы при обрыве VPN трафик не утекал напрямую.
- Сделать DNS leak protection.
- Сделать IPv6 leak protection.
- Сделать WebRTC leak guidance позже для браузеров.
- Сделать автоматическую смену сервера при деградации скорости или handshake.

## 14. Протоколы И Транспорты

Нам нужно не заменять WireGuard, а добавить несколько уровней на выбор.

Основной режим:

- WireGuard UDP.
- Быстрый, простой, хороший для обычной сети.
- Использовать как default, пока работает.

Fallback 1:

- WireGuard через нестандартные порты.
- Например 443/UDP, 53/UDP, дополнительные high ports.
- Нужно аккуратно тестировать, потому что разные провайдеры режут UDP по-разному.

Fallback 2:

- OpenVPN TCP 443.
- Медленнее, но часто живёт там, где UDP режется.
- Использовать как “надёжный аварийный режим”.
- Желательно tls-crypt/tls-crypt-v2, чтобы меньше светить control channel.

Fallback 3:

- Shadowsocks AEAD.
- Это не классический VPN, а encrypted proxy, но через TUN можно завернуть трафик.
- Полезен как дополнительный транспорт.
- Можно использовать плагины/обфускацию, если будет нужно.

Fallback 4:

- Hysteria2.
- QUIC/HTTP3-подход.
- Может быть полезен на плохих и нестабильных сетях.
- Может быть заблокирован там, где режут QUIC, поэтому не должен быть единственным вариантом.

Fallback 5:

- Trojan/VLESS-over-TLS/REALITY-подобные stealth-транспорты.
- Это не первый шаг, но мощный слой для сложных сетей.
- Нужно использовать аккуратно, потому что такие решения быстро меняются и требуют постоянного обслуживания.

Fallback 6:

- MASQUE/CONNECT-UDP/HTTP3 в будущем.
- Это перспективный слой, похожий на обычный HTTPS/HTTP3-трафик.
- Пока лучше держать как исследовательское направление, а не основу MVP.

Fallback 7:

- Pluggable transports-подход.
- Идея: транспорт можно заменить, не переписывая весь VPN.
- Вдохновляться obfs4, Snowflake, WebTunnel, но не обязательно тащить Tor внутрь нашего продукта.

## 15. Серверная Сетка

Нужно покупать дополнительные серверы не просто “где красиво”, а стратегически.

Первый этап:

- Нидерланды, текущий dev/prod-сервер.
- Германия.
- Швеция.
- Финляндия.
- Польша или Литва/Латвия/Эстония.

Второй этап:

- Франция.
- Великобритания.
- Турция.
- Грузия.
- Казахстан.
- США как дальний fallback.

Правило:

- Не держать всё у одного хостера.
- Не держать всё в одной стране.
- Не держать все протоколы на одном IP.
- Не держать API и VPN только на одном сервере.
- Не использовать личный Friendly-сервер.
- Разнести серверы по разным ASN/провайдерам.
- На один регион желательно минимум 2 провайдера.
- На важные страны желательно минимум 2 endpoint.

Минимальная коммерческая сетка:

- 5 стран.
- 2 провайдера на самые важные направления.
- 8-10 VPN endpoint.
- 2 backend/API endpoint.
- 1 monitoring endpoint.

“Титан” версия:

- 10-15 стран.
- 20+ endpoint.
- Разные провайдеры.
- Разные протоколы.
- Автоматический health scoring.
- Автоматическая выдача лучшего endpoint.
- Быстрое выключение плохих серверов.
- Быстрая ротация IP.

## 16. Автоматический Выбор Сервера

Пользователь не должен понимать, какой протокол сейчас работает.

Что нужно сделать:

- Кнопка Авто.
- Клиент проверяет доступность endpoint.
- Клиент проверяет latency.
- Клиент проверяет TCP/UDP/TLS.
- Клиент выбирает лучший вариант.
- Если WireGuard не работает, пробует fallback.
- Если сервер умер, переключается на другой.
- Если страна недоступна, переключается на другую.
- Если API недоступен, использует запасной bootstrap.
- Если всё плохо, показывает понятную ошибку и код отчёта для поддержки.

Логика выбора:

- Сначала быстрый WireGuard.
- Потом WireGuard на другом порту.
- Потом другой сервер той же страны.
- Потом соседняя страна.
- Потом TCP/TLS fallback.
- Потом stealth/fallback transport.
- Потом аварийный режим.

## 17. Защита От Блокировок

Нужно проектировать не “обход одной блокировки”, а устойчивость к разным типам блокировок.

Типы блокировок:

- Блокировка IP.
- Блокировка порта.
- Блокировка UDP.
- Блокировка WireGuard handshake.
- Блокировка DNS.
- Блокировка API-домена.
- DPI/fingerprint detection.
- Замедление определённого протокола.
- Блокировка конкретного хостера.
- Блокировка целой страны или ASN.

Ответные меры:

- IP diversity.
- Port diversity.
- Protocol diversity.
- Provider diversity.
- Country diversity.
- Signed server list.
- Fallback API domains.
- DoH/DoT для bootstrap.
- TLS-based fallback.
- QUIC-based fallback.
- TCP fallback.
- Obfuscation transports.
- Быстрая ротация endpoint.
- Мониторинг доступности из разных сетей.

## 18. Мониторинг Доступности YouTube, Discord, Telegram И Других Сервисов

Нужно заранее понимать, что через наш VPN перестал открываться важный сервис, раньше чем пользователь напишет злой комментарий в поддержку.

Идея:

- У нас есть monitoring agents.
- Они регулярно подключаются через наш VPN.
- Они проверяют доступность важных сервисов.
- Они сравнивают “без VPN” и “через Green VPN”.
- Они отправляют результат в backend/admin app.
- Если доступ через VPN сломался, админка показывает тревогу.
- Если проблема только на одном сервере, backend убирает этот сервер из авто-выбора.
- Если проблема в конкретном протоколе, клиентам выдаётся другой fallback.
- Если проблема массовая, админ получает alert.

Что проверять:

- YouTube.
- Discord.
- Telegram.
- Instagram, если нужно.
- WhatsApp, если нужно.
- TikTok, если нужно.
- Сайты/приложения из Social Only.
- Наш backend/API.
- Наши payment endpoint.
- Наши update endpoint.
- Наши bootstrap domains.

Типы проверок:

- DNS resolve.
- TCP connect.
- TLS handshake.
- HTTP status.
- Проверка redirect.
- Проверка загрузки маленького test endpoint.
- Проверка реального web-доступа через headless browser.
- Проверка Telegram API endpoint.
- Проверка Discord gateway/API endpoint.
- Проверка YouTube web и video metadata.
- Проверка latency.
- Проверка packet loss.
- Проверка скорости маленькой загрузки.
- Проверка через каждый VPN endpoint.

Как это должно выглядеть в админке:

- Карта серверов.
- Статус каждой страны.
- Статус каждого протокола.
- Статус каждого важного сервиса.
- Зелёный: всё работает.
- Жёлтый: деградация.
- Красный: сервис недоступен через конкретный endpoint.
- График доступности.
- История инцидентов.
- Автоматическая рекомендация: “убрать сервер из выдачи”, “переключить пользователей на Германию”, “отключить UDP endpoint”.
- Кнопка ручного отключения сервера.
- Кнопка ручного возврата сервера.
- Уведомления в Telegram/почту/админку.

Дешёвый первый этап:

- Один monitoring agent на нашем dev/prod-сервере.
- Один monitoring agent на отдельном маленьком VPS.
- Проверки backend/API/VPN endpoint.
- Проверки YouTube/Discord/Telegram через основной VPN.
- Простые alert в Telegram.

Средний этап:

- Monitoring agents в нескольких странах.
- Проверки каждого VPN endpoint.
- Проверки через разные протоколы.
- Автоматическое исключение плохого endpoint из server catalog.
- Статус-страница для админа.

Сильный этап:

- Private probes в разных сетях.
- Проверки из РФ-сетей, если это юридически и технически безопасно.
- Synthetic browser checks через Playwright/аналог.
- Отдельные canary-аккаунты.
- Автоматический incident workflow.
- Автоматическая деградация server score.
- Автоматическая ротация users на здоровые endpoint.

Важно:

- Проверки должны идти только с наших controlled agents.
- Не надо полагаться только на зарубежный VPS, потому что он не покажет проблемы российских пользователей.
- Нужно иметь хотя бы один probe, который имитирует реального пользователя из нужной сети.
- Нужно не просто пинговать сервер, а проверять реальный доступ к сервисам через VPN.

## 24. Дешёвый Старт И Постепенное Усиление

Сразу строить “монстра” будет дорого, поэтому делаем ступенями.

MVP-уровень:

- Один основной dev/prod-сервер.
- Один дополнительный сервер в Германии или Швеции.
- WireGuard как основной протокол.
- Один запасной порт.
- Простая проверка здоровья серверов.
- Простое обновление server catalog.
- Простая система обновлений клиента.
- Простые alert в Telegram.

Первый коммерческий уровень:

- 3-5 стран.
- 5-8 endpoint.
- Health scoring.
- Автоматическое исключение плохих серверов.
- OpenVPN TCP 443 как аварийный fallback.
- Нормальная система обновлений.
- Мониторинг YouTube/Discord/Telegram через VPN.
- Code signing.

Сильный уровень:

- 10+ стран.
- Разные хостеры.
- Несколько протоколов.
- Private monitoring probes.
- Автоматический fallback по протоколам.
- Signed server catalog.
- Staged rollout обновлений.
- Автоматический rollback.
- Отдельное админское приложение.
- Расширенная техподдержка.

Титановый уровень:

- 20+ endpoint.
- Multi-provider architecture.
- Protocol diversity.
- Obfuscation/stealth transports.
- Synthetic monitoring из разных сетей.
- Автоматическое переключение пользователей.
- Автоматическая ротация endpoint.
- Полная observability.
- Полноценная внутренняя админ-система.
- Команда поддержки/ops.

## Главная Мысль

Сначала делаем Green VPN настоящим Windows-приложением: service, tray, автозапуск, нормальный auth. Потом добавляем систему обновлений, чтобы приложение можно было развивать без ручной переустановки. Потом делаем коммерческий слой: платежи, тарифы, документы, code signing. Потом строим “титановый” VPN-layer: несколько стран, несколько протоколов, несколько провайдеров, автоматический fallback, мониторинг доступности сервисов и админку, которая узнаёт о проблемах раньше пользователей.
