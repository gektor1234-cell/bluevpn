# Как не раздувать контекст снова

Старый чат стал тяжёлым из-за длинных планов, множества скриншотов, повторов и больших отчётов. Новый чат должен работать иначе.

## Правило старта

В начале новой сессии читать только:

- `README_RU.md`
- `00_START_MESSAGE_RU.md`
- `01_PROJECT_STATE_RU.md`
- `03_NON_NEGOTIABLE_RULES_RU.md`
- `08_NEXT_DEVELOPMENT_TASKS_RU.md`

Полный мастер-план `02_MASTER_PLAN_FULL_RU.md` читать только когда нужно свериться с дорожной картой.

Старые большие docs читать точечно:

- `CODEX_CONTEXT_COMPACT_RU.md`
- `CURRENT_HANDOFF.md`
- `RELEASE_STATE.md`

Не читать все docs подряд без необходимости.

## Старый чат

Старый текущий чат разрешено использовать только как аварийный архив.

Когда можно:

- handoff-файлы противоречат друг другу;
- непонятно, почему принято конкретное решение;
- нужно восстановить точную историю installer/service/rollback бага;
- пользователь прямо просит свериться со старой перепиской;
- в коде и docs не хватает информации для безопасного решения.

Когда нельзя:

- в начале каждой сессии;
- вместо чтения `git status`, кода и handoff-файлов;
- ради повторного пересказа планов;
- ради старых скриншотов, если они не относятся к текущему багу.

Порядок источников истины:

- текущий код и `git status`;
- файлы handoff-пакета;
- `CURRENT_HANDOFF.md`, `RELEASE_STATE.md`, `CODEX_CONTEXT_COMPACT_RU.md`;
- старый чат только при крайней необходимости.

## Правило скриншотов

Скриншоты из старого чата не нужны, если задача не про конкретный визуальный баг.

Если пользователь прислал новый скрин:

- извлечь факт;
- записать факт в handoff, если он важен;
- дальше не держать скрин в рабочем контексте.

## Правило планов

Не переписывать полный мастер-план в чат каждый раз.

Если нужен план:

- сослаться на файл;
- дать краткий статус;
- указать следующий пункт.

## Правило отчётов

В финальном ответе:

- коротко;
- что сделано;
- что проверено;
- что требуется от владельца;
- прогресс.

Большие технические детали писать в docs, не в чат.

## Правило задач

Одна рабочая итерация должна иметь понятный слой:

- backend/admin;
- user client;
- installer;
- auth;
- payments;
- monitoring;
- docs.

Не смешивать всё сразу, если это не долгий автономный проход и нет явного согласия.

## После стабильного шага

Обновлять компактные файлы:

- `CURRENT_HANDOFF.md`;
- `RELEASE_STATE.md`;
- возможно `CODEX_CONTEXT_COMPACT_RU.md`;
- при необходимости отдельный small checkpoint doc.

## Если контекст снова пухнет

Создать новый каталог:

`docs\NEW_CHAT_HANDOFF_YYYY_MM_DD`

И туда положить:

- start message;
- current state;
- next tasks;
- release/rollback;
- secrets policy;
- deploy commands.

Не переносить старую переписку.
